# Player Precache and Chrome

**Status:** Completed
**Related product spec:** [`../../product-specs/ios-player-controls.md`](../../product-specs/ios-player-controls.md)

## Objective

After playback starts, keep downloading forward from the playhead into the existing prefetch cache. Draw that cached interval on the progress bar, show a loading indicator whenever playback is loading or buffering, and share one prefetch session with the scrub-preview reader.

## Scope

- `PrefetchSession` concurrent bodies, forward fill, and cache-span publication
- iOS and macOS progress bars, loading indicators, and scrub preview
- iPhone landscape presentation order and the macOS player window frame
- iOS Player Figma frames `604:2` and `604:12`; macOS Player frame `115:406`

## Out of Scope

- Baidu official download links
- Routing iOS `smb://` playback through the prefetch proxy
- Fixing the known 4K first-frame stall that appears after a media-server file is served through the prefetch proxy
- Unrelated product-domain grades in `QUALITY_SCORE.md`

## Decisions

- Forward fill stops at 180 seconds ahead of the playhead or 256 MiB stored in the session, whichever comes first. Memory stays at 64 MiB; the rest spills to the existing temporary store.
- The gray span is the contiguous cached byte range that contains the playhead, mapped linearly by file size. It is not KSPlayer's buffering percentage.
- Sources without a prefetch session and without AVFoundation `loadedTimeRanges` leave the gray span empty. Local files show the full duration as already local.
- Progressive Emby, Jellyfin, and Plex file URLs use the same localhost prefetch session as FTP and SFTP. HLS transcode playlists stay direct so AVPlayer still opens a `.m3u8` path. The 4K first-frame stall is deferred until this routing is in place.
- The macOS walk is operator-run from a signed Xcode build. The evidence binary traps in `CKContainer` init, and no Mac provisioning profile exists for `./run_device.sh --macos` (see 2026-09-29 Progress).
- Device logs and recordings under `tem/` are operator-local and not committed, because they contain the real server host. The Progress entries quote the lines they rely on.

## Risks

- Byte-to-time mapping is linear and is only a progress-bar hint.
- The macOS volume-slider window-drag guard has no device confirmation. Only the progress bar was checked.
- A scrub outside the gray span still waits for a range read on the shared session.
- iOS SMB does not grow a prefetch gray span. Media-server HLS playlists also stay direct.
- Serving a 4K Emby, Jellyfin, or Plex file through the prefetch proxy can again truncate the first response and delay the first frame. That fix waits for a separate test and plan.
- A quality change overlaps the previous prefetch unregister. The new session is kept only when `mediaGeneration` is unchanged; a cancelled reload can still lose one registration.
- Until the resume seek lands, a reported playhead below 1 second uses the pending start. Any later report of at least 1 second clears that pending start.
- The 360p Emby HLS freeze was never captured with a frozen-state backtrace. The `log07` build differed from `log06` by the PiP publish guard plus DEBUG main-queue probe and checkpoint logs. With one run each, the guard is the most likely cause, but that is inferred, not proven. The final build differs from the `log07` device build only by removing DEBUG-only logging and the probe, and the operator accepted `log07` as its device evidence. If a freeze returns, capture the Thread 1 `bt` first.
- `KSOptions.preferredFrame = false` keeps KSPlayer's iOS display link at the screen rate during playback (60 Hz on iPhone, up to 120 Hz on ProMotion iPad). The panel can no longer drop to 24, 30, or 48 Hz for video, and main-thread display callbacks rise several times. Power cost on a long session is unmeasured.
- The PiP guard still publishes inside `updateUIView` when the possible/active value actually changes. If a freeze returns, defer that refresh off the view update or observe the controller through KVO.
- `HlsTranscodePrimer.prime` takes about 7.4 to 7.6 seconds before the engine opens, in both the frozen and the healthy run (`log06`: 10:35:34.04 to 10:35:41.41; `log07`: 10:48:09.25 to 10:48:16.85). That is a startup-latency issue, separate from the freeze.
